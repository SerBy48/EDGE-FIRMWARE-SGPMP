## 1. Diagnóstico

En el Edge, "el parser" es el camino que convierte una entrada en una lectura
clasificable:

```
trama LoRa → decode (protocol.py) → Reading (gateway.py) → agente → motor RF-55 (evaluador.py)
```

El reporte no confirmaba ningún fallo porque la prueba quedó en `SKIPPED`. Al
ejecutar entradas nulas y malformadas contra el código real **sí aparecieron
clasificaciones válidas falsas**:

| Entrada | Resultado antes de la corrección | Defecto |
|---|---|---|
| T = `inf` con HR válida (`ESTRES_TERMICO`) | `DESVIACION_COMPUESTA` `CRITICO` | Clasificación falsa |
| HR = `true` (`ESTRES_TERMICO`) | `DESVIACION_COMPUESTA` `LEVE` | Clasificación falsa |
| pH u OD = `inf`, `-inf` o `true` (`CALIDAD_HIDRICA`) | `DESVIACION_COMPUESTA` `CRITICO` | Clasificación falsa |
| HR = 150 %, pH = −3 o 20, OD = −1 | `DESVIACION_COMPUESTA` (varias `CRITICO`) | Valores físicamente imposibles clasificados |
| `null` o `"abc"` en una regla compuesta | `ERROR_CONFIGURACION` | Culpa a la regla cuando el problema es el dato |
| Trama LoRa con float NaN/∞ | Aceptada; telemetría con `"valor_crudo": NaN` | JSON inválido hacia el broker |

**Causa raíz:** las fórmulas Tipo B (`ESTRES_TERMICO`, `CALIDAD_HIDRICA`) no
validaban la lectura que disparaba la evaluación (solo las que buscaban en la
ventana), y no había validación de rango físico ni de finitud en la entrada
LoRa. El umbral simple (RF-55.1) y las reglas Tipo A ya descartaban bien los
valores no numéricos.

## 2. Cambios necesarios para QA

### 2.1 Contrato de entradas inválidas

Una lectura inválida **se rechaza antes de clasificar**: no genera ningún evento
(ni `DESVIACION_*` ni `ERROR_CONFIGURACION`), se registra con WARNING y queda
marcada en el historial local como `LECTURA_INVALIDA` con su motivo.

| Entrada | Inválida |
|---|---|
| `null`, texto (incluido `"31.0"`), booleano | Siempre |
| NaN, +∞, −∞ | Siempre |
| `humedad_relativa` | Fuera de [0, 100] % |
| `ph` | Fuera de [0, 14] |
| `oxigeno_disuelto` | Negativa |

- Los bordes (HR 0 y 100, pH 0 y 14, OD 0) son válidos.
- Las demás lecturas válidas de la misma captura se clasifican normalmente.
- Un dato inválido no entra a la ventana de correlación: no puede combinarse
  con lecturas posteriores.
- La trama LoRa con una medición NaN/∞ conserva las demás mediciones; solo esa
  se descarta.
- Un valor fuera de rango físico (p. ej. HR 150 %) **sí** viaja como telemetría
  cruda (la valida el DTO del backend, G58), pero no se clasifica. NaN, nulos o
  texto no se envían como telemetría.

### 2.2 Matriz de resultados esperados para TC-M03-081

| Entrada | Esperado |
|---|---|
| Cualquier valor de §2.1 en una lectura con umbral simple | Sin evento; `LECTURA_INVALIDA` en historial |
| T o HR inválida con regla THI | Sin evento (ni `DESVIACION_COMPUESTA` ni `ERROR_CONFIGURACION`) |
| pH u OD inválido con regla de calidad hídrica | Sin evento |
| T = 30 °C válida + HR `null` en la misma captura | Solo `DESVIACION_SIMPLE` `CRITICO` de T (por su umbral) |

### 2.3 Cómo ejecutarlo

```bash
cd raspberry
pytest tests/test_parser_entradas.py -v                       # 51 pruebas: matriz completa
python scripts/inyectar_lecturas.py scripts/casos_rf55.json -v --caso "P1 TC-M03-081 humedad nula con THI"
python scripts/inyectar_lecturas.py scripts/casos_rf55.json -v --caso "P2 TC-M03-081 pH no numerico y OD booleano"
python scripts/inyectar_lecturas.py scripts/casos_rf55.json -v --caso "P3 TC-M03-081 fuera de rango fisico (HR 150 %, pH 20)"
python scripts/inyectar_lecturas.py scripts/casos_rf55.json -v --caso "P4 TC-M03-081 la lectura valida de la captura se sigue clasificando"
```

El inyector acepta `"valor": null`, texto y booleanos en `lecturas` para
armar casos propios. Con `-v` imprime el historial con cada `LECTURA_INVALIDA`
y su motivo. En el nodo físico, la misma evidencia se obtiene con
`python -m edge_agent.inspeccionar historial --clasificacion LECTURA_INVALIDA`
(ver INC-M03-108-G40 §2.3).

### 2.4 Alcance

Esta prueba cubre la capa Edge. La validación del DTO del backend (G58) es
otra capa y sigue siendo necesaria; no se sustituyen entre sí.

## 3. Decisión y abordaje en el repositorio

### 3.1 Decisiones

| # | Decisión | Motivo |
|---|---|---|
| D1 | Una sola validación de entrada al inicio de `evaluar_lote`, antes de cualquier regla | Cubre umbrales, Tipo A, Tipo B y fórmulas futuras sin repetir chequeos en cada una |
| D2 | Lectura inválida → sin evento, WARNING y `LECTURA_INVALIDA` en el historial local | El contrato pide rechazar o marcar sin clasificar; publicar un evento de "dato inválido" no está en el contrato del backend |
| D3 | No usar `ERROR_CONFIGURACION` para datos malos | Ese evento significa regla o umbral inutilizable; mezclarlo confundiría el diagnóstico |
| D4 | Rangos físicos solo para HR, pH y OD | Son los únicos con límites físicos inequívocos; para temperatura rige el umbral RF-17 (fuera de bandas = `CRITICO`, decisión vigente) |
| D5 | NaN/∞ se descartan en el Gateway LoRa por medición, no por trama | Una medición rota no debe hacer perder las demás de la misma trama |
| D6 | Fuera de rango físico sí viaja como telemetría | Es el dato crudo que llegó; el backend decide con su propia validación |
