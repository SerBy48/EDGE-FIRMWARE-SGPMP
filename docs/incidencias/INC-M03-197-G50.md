## 1. Diagnóstico

| Caso | Comportamiento antes | Defecto |
|---|---|---|
| Fórmula con 4 variables requeridas (TC-086) | `ACK_REGLA` `ERROR` al recibirla, no se evalúa | — (ya cumplía) |

El motor solo tenía `MAX_VARIABLES_POR_REGLA = 3`. Los nombres
`CARDINALIDAD_MIN`/`CARDINALIDAD_MAX` que cita el reporte son de los scripts de
QA, no del firmware.

## 2. Cambios necesarios para QA

### 2.1 Definición única

| Límite | Valor | A qué aplica |
|---|---|---|
| Mínimo | **2** variables requeridas | Reglas Tipo B (fórmula del catálogo) |
| Máximo | **3** variables requeridas | Reglas Tipo B |
| Opcionales | No cuentan | Solo modifican el resultado (THI: 2 requeridas + 2 opcionales es válida) |
| Tipo A | No aplica | No correlaciona variables: confirma **una** variable repetida en el tiempo |

Fuera de rango → `ACK_REGLA` `ERROR` al recibir, con
`motivo: "regla inválida: <CODIGO> correlaciona N variable(s) (mínimo 2, máximo 3)"`.
La regla no se guarda ni se evalúa. Si una regla así llegara guardada por otro
firmware, se reporta `ERROR_CONFIGURACION` una vez y no produce
`DESVIACION_COMPUESTA`.

### 2.2 Cómo verificarlo

El catálogo de fórmulas es cerrado y no se amplía por red (decisión de
seguridad de RF-55.2): **no existe** hoy una fórmula publicada de 1 ni de 4
variables, así que no se puede provocar desde la plataforma ni con el inyector.
Se verifica con `pytest`, que inyecta la fórmula en el catálogo y pasa por el
manejador real del comando `REGLA_COMPUESTA`:

```bash
cd raspberry
pytest tests/test_reglas_compuestas.py -v -k "variable or cardinalidad"
```

| Prueba | Verifica |
|---|---|
| `test_formula_con_4_variables_se_rechaza` | TC-086: `ACK_REGLA` `ERROR`, regla no guardada |
| `test_formula_con_1_variable_se_rechaza` | TC-107 E1: `ACK_REGLA` `ERROR` (aunque tenga opcionales); guardada → `ERROR_CONFIGURACION`, nunca compuesta |
| `test_cardinalidad_cuenta_solo_las_variables_requeridas` | THI (2+2) se acepta; todo el catálogo publicado cumple [2, 3] |
| `test_tipo_a_con_una_variable_no_aplica_cardinalidad` | Tipo A con una variable sigue siendo válida |

### 2.3 Punto para Análisis/QA

Una regla **Tipo A** (ventana de confirmación) usa una variable y emite
`DESVIACION_COMPUESTA` con `regla_aplicada: "VENTANA_CONFIRMACION"`: su
"composición" es temporal (N lecturas en M minutos), no entre variables. Si la
matriz de TC-M03-107 E1 usa una regla Tipo A, el resultado esperado debe ser
`DESVIACION_COMPUESTA` `VENTANA_CONFIRMACION`, no un rechazo. Cambiar esa
etiqueta afectaría al backend y está fuera de este cambio.

## 3. Decisión y abordaje en el repositorio

### 3.1 Decisiones

| # | Decisión | Motivo |
|---|---|---|
| D1 | `MIN_VARIABLES_POR_REGLA = 2` para Tipo B | Una sola variable no es una correlación |
| D2 | El máximo y el mínimo cuentan solo las requeridas | THI tiene 2 opcionales de escalada; contarlas rechazaría la regla de referencia |
| D3 | Tipo A queda fuera de la cardinalidad | Es confirmación temporal de una variable por diseño (decisión RF-55 n.º 4) |
| D4 | Sin límite en el payload del backend | Rechazaría eventos válidos sin corregir la configuración del nodo |
