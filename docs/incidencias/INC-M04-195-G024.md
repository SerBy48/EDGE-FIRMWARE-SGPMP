## 1. Diagnóstico

QA no puede ejecutar los dos subcasos porque faltan dos insumos: un CSV de
validación etiquetado con `nivel_riesgo` 0–3 y la URL de un nodo Edge
accesible y aislable. Revisé el firmware y el broker, y **ninguno de los dos
insumos puede salir de ellos**:

| Insumo | Situación en el firmware / broker |
|---|---|
| Motor de IA en el Edge (RF-66) | **No implementado.** El Edge corre RF-55, un motor de reglas determinista, no inferencia de ML (`CONTRATO_EVENTO_EDGE.md`, introducción). Los comandos `CONFIG_MOTOR_IA` y `TIPO_MODELO_ASIGNADO` se rechazan con `ACK_CONFIG_MOTOR` / `ACK_TIPO_MODELO` `resultado: "ERROR"`, "tipo de comando no soportado" |
| Dataset etiquetado `nivel_riesgo` 0–3 | El Edge no produce `nivel_riesgo` ni conserva etiquetas; sus clasificaciones son `NORMAL` / `DESVIACION_SIMPLE` / `DESVIACION_COMPUESTA` con severidades. El dataset es del equipo de IA/datos que entrena `MODELO_RIESGO_CONTAGIO` |
| URL del nodo Edge | El `edge-agent` **no expone HTTP**: solo es cliente MQTT. No hay URL que el comando `disponibilidad` pueda sondear |
| Broker | Solo reenvía telemetría, eventos, heartbeats y OTA; no tiene nada de `/prediccion/motor-ia` ni de modelos |
| `f1_score` / `recall_clase_riesgo_alto` en `null` (RF-69) | Registro de versiones de modelo en el backend; el Edge no lo escribe |

Además, el subcaso 2 es contradictorio tal como está planteado: medir una
disponibilidad "sin dependencia de red" sondeando una URL por red mide la red,
no el nodo.
